二、问题清单

P0  首页 React 水合失败（React error #418）

影响面：Best Practices 被扣分只是表象。#418 意味着 React 放弃了整个根节点的服务端 HTML，改在客户端重新渲染整棵树 —— 你精心做的 SSR 首屏实际上被丢掉了， SEO 抓到的是一份「和真实渲染不一致」的 DOM，首屏渲染成本也顺带被推高。

实测证据：

  • / → 每次访问都抛 #418（桌面、移动、全新 profile，各 3/3 复现）
  • /posts、/about、/photowall → 完全没有报错。问题只出在首页
  • 抓取首页 SSR HTML 与「水合后的 DOM」逐节点 diff，首屏外壳出现结构性差异：
// 服务端渲染出来的（未激活）
<a class="flex shrink-0 items-center gap-2.5 ... select-none" href="/">
<a class="nav-item ... border-transparent text-ink-3 ..." href="/">首页</a>
//   → 全文 0 处 aria-current="page"

// 客户端首帧渲染出来的（激活）
<div class="flex shrink-0 items-center gap-2.5 ... cursor-pointer">
<a aria-current="page" class="nav-item ... border-accent-hairline bg-accent-soft ...">首页</a>

// 对比 /posts、/about 页面的 SSR：aria-current="page" 正常出现 2 次 ✅

根因：首页服务端渲染阶段，usePathname() 拿到的值不是 "/" （其余页面正常）。Navbar 里的这段逻辑把「是否激活」直接映射到了不同的元素类型：

// components/layout/Navbar.tsx（现状）
{isActive("/", pathname)
  ? <div className={`${brandClass} cursor-pointer`}>…</div>   // 客户端走这里
  : <Link href="/" className={brandClass}>…</Link>}      // 服务端走这里

<a> ↔ <div> 是元素类型不一致，React 无法用打补丁的方式修复，只能整树重渲染并抛 #418。 <html> 上的 suppressHydrationWarning 对这个级别的失配无效。

已验证的修复方向：把首页 SSR 输出的导航改成与客户端一致的「激活」结构后， #418 完全消失（实测：错误数 1 → 0）。也就是说修复点确实在导航的 pathname 分支上。

建议改法（双保险）：

// 1) 归一化，保证服务端与客户端首帧取到同一个值
const pathname = usePathname() ?? "/";

// 2) 品牌位不再切换元素类型，激活态只体现为 class / aria-current
<Link href="/"
      className={`${brandClass} cursor-pointer`}
      aria-current={isActive("/", pathname) ? "page" : undefined}>
  {brandText}
</Link>

改完请重新跑一次审计确认 #418 归零；若 usePathname() 仍返回 null 导致首页激活态丢失， 再叠加「挂载后再上激活态」的门控写法（useEffect 里 setMounted(true)，首帧统一按未激活渲染）。

P1  首屏元素渲染延迟 1.1~1.8 s —— LCP 的真正瓶颈

证据（LCP breakdown）：

阶段桌面端移动端
Time to first byte537 ms416 ms
Resource load delay54 ms—
Resource load duration33 ms—
Element render delay1801 ms1132 ms

图片早就下载好了（load duration 只有 33 ms），但浏览器迟迟不肯画出来。原因在 app/globals.css：

/* app/globals.css:516 */
[data-reveal] {
  opacity: 0;                              /* ← 首屏内容初始完全透明 */
  transform: translateY(var(--reveal-y, 2.5rem));
  transition: opacity 500ms ease-out, transform 500ms cubic-bezier(...);
  transition-delay: var(--reveal-delay, 0ms);  /* 首屏最晚还叠加 240ms */
}
[data-reveal][data-revealed="true"] { opacity: 1; }

首页有 7 处 data-reveal，其中的首屏三块（SearchBar、ProfileCard + CloudPlayer、图片宫格） 都挂着它。而 data-revealed 只能由 RevealObserver 在水合之后写入，于是 LCP 被串成了： JS 下载 → 水合 → rAF → 写入属性 → 500ms 过渡 + 最多 240ms 延迟。 这条链路里任意一环变慢，内容就一直不可见。

建议改法：

  • 首选：直接摘掉首屏元素的 data-reveal（SearchBar / ProfileCard / CloudPlayer / 首屏图片格）， 只保留 SiteDashboard 这类首屏之外的动画。改动最小、收益最大。
  • 或改成不依赖水合的纯 CSS：用 @starting-style + animation，或 animation-timeline: view()（注意 Safari 支持度，需回退）。
  • 顺带一提：HomeClient.tsx 里那段「3 秒内把滚动位置强行拉回顶部」的 guardScroll （window.scrollTo(0,0) + 多组监听）会干扰用户操作，建议一并删掉或大幅缩短。

P1  图片投递浪费 53 ~ 67 KiB

证据：Lighthouse Improve image delivery 报「Est savings of 67 KiB（桌面）/ 53 KiB（移动）」， LCP 元素就是这张：

src="https://picx.zhimg.com/v2-394d2ecadb292765ac1d810cbe5672b3_1440w.jpg"
渲染尺寸：715 × 218 CSS px     实际文件：1440w JPEG / 67 KB
<img> 上只有 sizes=""，没有 srcset → sizes 完全不生效，也没有 AVIF/WebP 转换

根因：components/ui/SafeImage.tsx 对不在白名单内的域名会降级成原生 <img>，而白名单只有两个域名：

// app/lib/image-hosts.ts
const STATIC_IMAGE_HOSTS = [
  "avatars.githubusercontent.com",
  "api.dicebear.com",
];   // ← 没有 picx.zhimg.com，也没有 img.lts.cc

好消息是 img.lts.cc 的缩略图本身已经是 WebP 且体积很小（实测 25.5 KB / 32.1 KB，走 /thumb/ 目录），所以真正被浪费的只有知乎图床那张封面。

建议改法（按推荐度排序）：

  1. 统一走自己的图床缩略图（与 photoWall / moments 一致）：保存文章封面时就写入 CDN， 读取时用 thumbUrlOf() 拼 /thumb/ 路径。架构上最一致，长期最省事。
  2. 把 picx.zhimg.com 加进 STATIC_IMAGE_HOSTS，走 next/image （IMAGE_REMOTE_PATTERNS 是用同一个数组生成的，会自动带上）。注意该图床可能有防盗链，需确认服务端抓取可用。
  3. 最省事的临时手段：把封面 URL 换成小尺寸 / WebP 变体，避免 1440w 直出。

另外：首屏有 3 张图同时标了 fetchPriority="high" （相册封面、文章封面、说说封面），HTML 里对应 3 条 <link rel="preload" as="image">。 三张图互相抢带宽，反而会拖慢真正的 LCP 元素。建议只给最靠上的那张保留 priority，其余去掉。

结构性原因：首页 HomeClient.tsx 是单个巨型 client 组件， 把 SearchBar、CloudPlayer、LyricBar、三个 Carousel、SiteDashboard 全部静态 import，因此一律进首屏 bundle。另外 MusicProvider（410 行）挂在全局 layout.tsx 里，每个页面都要付这份成本，且挂载后会 fetch 歌单 （cache: "no-store"）；SiteConfigProvider 还会每 60 秒轮询一次 /api/site-config。

建议改法：

// 1) 首屏之外 / 非关键的客户端组件改懒加载（ClientWidgets 里已有这个范式）
const SiteDashboard = dynamic(() => import("@/components/widgets/SiteDashboard"), { ssr: false });
const CloudPlayer   = dynamic(() => import("@/components/music/CloudPlayer"));
const LyricBar      = dynamic(() => import("@/components/music/LyricBar"));

// 2) MusicProvider 不再无条件包住全站：改为「音乐真正用到时才挂载」
//    （例如只在 /music 页 + 用户点击播放后挂载），可让所有非音乐页面省掉这部分

// 3) SiteConfigProvider 的 60s 轮询去掉，改为 ISR/缓存 + 后台改动后主动 refresh
关于 Legacy JavaScript 和 polyfill chunk：你已经用 .browserslistrc 收紧过一次目标， 而且那个 113 KB 的 polyfill chunk 带 noModule —— 现代浏览器根本不会下载它， 真正的 Legacy JS 扣分只有 13.7 KB。所以「继续收紧 browserslist」的收益很有限， 不建议为此牺牲微信内置浏览器的兼容性。这条优先级放在最后。

四、修复记录（本次已实施）

P0 根因补充（这次定位到了真正的触发点）：水合失败不是 class / aria 这类属性差异造成的 —— 属性差异 React 19 会自行修正。 真正让 React 放弃整棵树的是结构差异，一共两处，都在导航里： 品牌位服务端渲染 <a>、客户端渲染 <div>， 以及 激活圆点 <span> 客户端有、服务端没有（{active && <span/>} 写法导致子节点数量不同）。 导航挂在 layout 上、不在任何 Suspense 边界内，所以这种结构差异会直接升级成根节点级 #418。

验证方式：抓取线上 SSR HTML，只把上述两处结构对齐客户端（class / aria-current 一律保持服务端的原样）， 用 Puppeteer 拦截响应重放 —— 错误数 1 → 0。
另外，把当前源码在本地跑一次生产构建（Next 16.2.4，Turbopack）后， 服务端在根路由拿到的 pathname 是 "/"、激活圆点也在 —— 说明线上那份构建与当前源码并不一致， 建议重新部署后再复跑审计。本次修复刻意做成不依赖服务端 pathname 取值是否正确，两种情况都不会再报 #418。

文件改动对应问题

本次验证结果

  • 水合：本地生产构建 + 真实浏览器（Edge headless）跑首页，#418 报错数 0； 再做一组对照 —— 故意把服务端 SSR 的激活态判到另一条路由上（只改 class、不动结构）， 水合依然 0 报错，证明修复对服务端 pathname 取值免疫。
  • Accessibility：本地 Lighthouse 桌面端 100（基线 95）， heading-order、target-size、label-content-name-mismatch 三项全部通过。
  • 工程校验：npx tsc --noEmit 与 npx eslint 均无输出（通过）。
  • 待办：Performance 与 Best Practices 的分数对比必须重新部署后再跑 —— 本次改动上线前，"0 个水合报错"与"图片实际优化收益"都需要以线上构建为准。
  • 刻意未动：HomeClient 里那段「3 秒内强制把滚动位置拉回顶部」的 guardScroll （属产品行为，不是性能问题）；MusicProvider 仍挂在根 layout（拆出去需要重排路由组结构，风险大于收益）。
