# HaoBlog 后台改造方案

> **项目定义**：把 HaoBlog 博客后台从「深色侧边栏 + 10 个平级入口」改造为对齐「逸刻博客管理平台」的白色扁平结构 —— 侧边栏 10 项收敛为 7 项，样式全面对齐参考截图，功能做合并与集中而非删除。
> **成功标准**：① 侧边栏、顶栏、统计卡、列表页、媒体库、设置页与参考截图逐区对齐；② 侧边栏入口 10 → 7；③ 后端 API 不删、数据不丢，旧链接可访问；④ `tsc --noEmit` + `eslint` 保持 0 错 0 警基线。
> **参考来源**：知乎作者 yike《逸刻博客管理平台》产品介绍（编辑于 2025-02-21）+ 用户提供的 8 张后台截图。
> **产出角色**：前端体验工程师（信息架构与视觉规格）→ 首席交付架构师汇编。

### 2.5 媒体库（新建，用户决策 1）

#### 数据来源：已有 `image_upload` 表，无需遍历 S3

现状核实结果（`prisma/schema.prisma:292`、`app/api/upload/image/route.ts:122`、`app/api/upload/presign/route.ts:79`）：

```prisma
model ImageUpload {
  id         String   @id @default(ulid())   // ulid，本身即时间有序
  url        String   @unique
  asset_id   String   @default("")           // = S3 object key：{category}/{folder}/{文件名}
  created_at DateTime @default(now())
  @@map("image_upload")
}
```

- 客户端 `uploadImage()`（`components/admin/lib.ts:261`）优先走 `/api/upload/presign` 直传，失败回退 `/api/upload/image` 中转；**两条路径都会写这张表** → 「所有上传图片自动出现在媒体库」这条机制**已经天然成立**
- `created_at` 支持时间倒序分页
- `asset_id` 可解析出 **category**（`UPLOAD_CATEGORIES` = posts / photowall / projects / moments / system，见 `app/lib/upload-rules.ts:10`）与 folder → **正好作为参考图的「分组胶囊」维度**

#### 新增 API：`app/api/files/route.ts`

| 方法 | 语义 | 说明 |
|------|------|------|
| `GET` | 分页列表 | 参数 `page` / `pageSize`(默认 48) / `category` / `q`(按文件名模糊)；返回 `list`(id, url, key, created_at)、`total`、`counts`(各 category 计数 + 全部)，用于胶囊计数 |
| `DELETE` | 删除 | 复用现有 `deleteImageByUrl`；批量删除由前端分批（≤10/批）调现有 `DELETE /api/upload/image?url=` 即可，**不必新增批量接口** |

鉴权：`requireAdmin`，与其他后台 API 一致。

#### 新增页面：`app/admin/(panel)/files/page.tsx` + `components/admin/MediaLibraryClient.tsx`

对齐参考图第 5 张：
- 标题 + 右上「上传」按钮
- 分组筛选胶囊：全部 / 文章 / 相册 / 项目 / 随笔 / 系统（各带计数）
- 批量操作条：全选、已选择 N 项、取消选择、删除
- 图片网格（5 列响应式），文件名截断，悬停显示「复制外链 / 删除」
- 分页

#### 新增选择器：`components/admin/MediaPicker.tsx`

- 弹窗形态：顶部搜索 + 分类胶囊 + 网格多选 + 底部「取消 / 确定(N)」
- **接入方式**：给 `ImageUploader` 增加「从媒体库选择」按钮（`mode="single"` 单选、`mode="multi"` 多选），选中项直接走现有 `onChange`，**不改动 ImageUploader 的上传逻辑**
- 覆盖面（现有 6 个插图文案点，全部自动受益）：`PostEditor`、`ProjectEditor`、`AlbumEditor`、`MomentsClient`、`ConfigGroupsEditor`（站点 logo 等）、`app/admin/(panel)/about/page.tsx`
- `AlbumEditor` 内另有独立的上传逻辑（`AlbumEditor.tsx:255` 批量传相册照片），同样补上选库入口

#### 三个必须处理的风险

1. **历史图片缺口**：`image_upload` 表随 `20260930000000_init` 迁移建立，此前上传的图片没有记录 → 媒体库看不到老图。需要一次性回填：从 `Post.cover`、`Photo.url`、`Chatter.images`、`Project.cover_image`、`Album.cover`、站点配置的图片字段反向写入 `image_upload`（写一个 `scripts/backfill-image-upload.mjs`，幂等 upsert）。**回填前媒体库只能显示新上传的图**。
2. **脏记录**：presign 路径是「先写表、后 PUT」，若浏览器 PUT 失败会留下指向不存在对象的记录 → 网格破图。处理：网格 `onError` 兜底显示占位 + 后台提供「清理失效记录」动作（可选，Phase 内做）。
3. **删除语义**：媒体库删除会物理删除 S3 对象，若该图正被文章/相册引用则前端破图。处理：删除前查引用（扫 Post.cover / Photo.url / Chatter.images 等字段）并提示「该图正被 N 处使用」；批量删除同样先校验。至少要做到「有引用时二次确认」。

## 九、决策与权衡

| 决策 | 采用方案 | 被否决的备选 | 否决原因 |
|------|---------|-------------|---------|
| 媒体库数据源 | **查 `image_upload` 表** | 遍历 S3 ListObjectsV2 | 表已存在且上传即写入，天然满足「所有上传图片都显示」；表查询可分页、可分分类计数、可排序，S3 遍历还要处理私有桶代理与性能 |
| 侧边栏结构 | 扁平 7 项、白底 | 保留原 3 组分组、仅换色 | 参考图是无分组扁平；分组标题在 7 项规模下反而增噪 |
| 项目管理 | 并入「博客文章」Tab | 保留独立菜单 | 与文章同构（封面+正文+分类标签），合并收益最大且正好对齐参考图「博客文章\|项目产品」 |
| 设置页 | 四页合一 | 保留三个独立设置入口 | 参考图「用户设置」即单页多区块；分散入口是当前最受诟病的碎片化来源 |
| 主题色 | 靛蓝 → 蓝 #2563eb | 沿用现有靛蓝 #4f46e5 | 参考图主色为蓝，且靛蓝与该配色的浅色卡片体系不协调 |
| 总览首卡 | 媒体文件**数量** | 空间占用 MB | 需遍历 S3 或加字段补采，成本与收益不匹配 |
| 评论管理 | 各页保留 Tab（决策 3） | 全部上收总览 | 用户明确要求保留 |
| 深色模式 | 本期不做（决策 5） | 与浅色同期交付 | 逐 token 调色 + 全页面回归会显著拖长 P1，先保证浅色对齐质量 |
